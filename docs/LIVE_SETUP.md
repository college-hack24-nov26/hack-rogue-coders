# Live setup

For the database connection, follow the [step-by-step Neon guide](NEON_SETUP.md). After changing `.env`, use `restart-local.ps1` to reload API/worker configuration; `run-local.ps1` intentionally reuses already running services.

Store API and worker credentials in the root `.env`. The root `.env.example` lists all server settings with safe defaults and blank secrets. Git ignores `.env` and `.env.*` overrides while allowing `.env.example` to be committed. Preserve existing `.env` values when adding configuration.

The mobile app's separate environment example contains only the public API address. Server credentials must stay out of `EXPO_PUBLIC_` variables and frontend bundles.

For a local farmer account, open `http://127.0.0.1:8081`, choose **Create farmer account**, enter your email, password (at least 10 characters) and matching confirmation, then choose **Create account**. The app signs you in after successful creation. Existing accounts use **Sign in**. This local development flow works with the existing local signing key; it does not require Neon or Gemini credentials. After an app update, use Ctrl+F5 to load the rebuilt screen.

The farmer login/signup pages have no API URL or provider-token controls. Developers set the public `EXPO_PUBLIC_API_URL` in `apps/farmer-mobile/.env` (see its `.env.example`) and rebuild the app. This public address is separate from private server credentials in the root `.env`.

Work from `C:\Jalsathi`. Keep existing `.env` values. The local database, login and private photo pipeline already work without provider accounts. The requested Neon, Gemini and WhatsApp services require credentials for your own accounts; their currently empty values cannot be generated by an application patch.

Run:

```powershell
.\.venv\Scripts\python.exe -m scripts.check_readiness --live
```

This writes `docs/READINESS.json`, lists exact missing variable names, and performs only read-only connection checks when configuration is complete. It prints no credential values and sends no messages. Successful metadata access does not establish login/recovery, signed uploads, AI generation or WhatsApp delivery. The system-admin portal shows the same configuration status under **Sources & data flow**.

| Service | Set in the local `.env` |
|---|---|
| Neon database | `DATABASE_URL` using `postgresql+psycopg://` and TLS settings from the Neon connection panel |
| Neon Auth | `NEON_AUTH_URL`, `NEON_AUTH_JWKS_URL`, `NEON_AUTH_ISSUER`, `NEON_AUTH_AUDIENCE`, `NEON_AUTH_ORIGIN`, `SESSION_ENCRYPTION_KEY`; enable `AUTH_MODE=neon` when the provider is configured |
| Private storage | `STORAGE_ENDPOINT`, `STORAGE_BUCKET`, `STORAGE_ACCESS_KEY`, `STORAGE_SECRET_KEY`; select `STORAGE_MODE=s3` only after private-bucket/signed-upload validation |
| Gemini | `GEMINI_API_KEY`, `GEMINI_MODEL` accessible to that key |
| WhatsApp | `WHATSAPP_APP_SECRET`, `WHATSAPP_VERIFY_TOKEN`, `WHATSAPP_ACCESS_TOKEN`, `WHATSAPP_PHONE_NUMBER_ID`, `WHATSAPP_API_VERSION`; configure the signed webhook callback `/api/v1/webhooks/whatsapp` in your Meta application |

Restart API/worker processes after changing environment values. For a new database, apply migrations with `.\.venv\Scripts\python.exe -m alembic upgrade head`. Preserve the existing SQLite database; changing the connection does not migrate its users/reports to Neon. Any transfer needs a reviewed migration.

The read-only diagnostic intentionally leaves `ALLOW_EXTERNAL_SEND=false`. Approved template/consent checks and an explicitly authorized delivery test are separate from connection checks. Neon signup/recovery can send emails and also remain gated.

The numerical release gate also requires authoritative source sign/publication-availability evidence, reviewed station/village/aquifer mappings, passing 15-horizon evaluations and human release approval. Credentials alone cannot supply that evidence. No model is automatically approved by training or import.
